# wgopt5 — Wi-Fi / FreeRTOS профилирование провала throughput

## Исходная точка

База: **проверенная диагностическая wgopt4**, коммит \`dc50dd5eaeb247c0d42e9d76ede7bc95dd091c0c\`. Пин microlink \`eb63b97073e529d57bc9c1deaeea25ac304034e5\` неизменён. Production \`main\`, NVS, сертификаты, ключи, маршрутизация, ChaCha20, Wi-Fi конфигурация, partitions и штатные релизы не изменены. Версия кандидатного образа \`0.1.35-tuya-wgopt5\`.

Три 120-сек теста \`iperf3 -c 192.168.0.146 -R -t 120 -i 10\`: wgopt2 5.83, wgopt3 5.72, wgopt4 5.92 Мбит/с (receiver). Во всех трёх: первые 40с ~7.2, следующие ~70с ~4.6–5.4, последние 10с ~7.2 Мбит/с. wgopt4 показывала, что при падении числа WG TX-пакетов время шифрования остаётся 438–443 мкс, direct error=0, дерп практически нет, внутренняя RAM ~41.7KiB. Значит, причина падения на уровне внутри/вне ЭСП всё ещё НЕ установлена; нельзя автоматически считать виновными ChaCha20, CPU или Wi-Fi.

## Новые измерения wgopt5

Используется уже существующий 10-секундный низкоприоритетный \`wg_diag\` reporter. К двум \`WG4_TX\`/\`WG4_RX\` строкам добавляется одна \`WG5_SYS\`, время \`t_ms\` синхронизировано по uptime ESP. Новая строка содержит:

- \`sta=0/1\`, \`rssi\` (дБм), \`ch\`, \`phy11n\` (0/1), \`ps\` (код режима энергосбережения; 0 — выключен, 1 — MIN_MODEM, 2 — MAX_MODEM; -1 — не удалось прочитать).
- \`cpu0_busy\`, \`cpu1_busy\` — занятость соответствующих ядер в % по **дельтам IDLE0/IDLE1 runtime stats**.
- \`wifi_task\`, \`tcpip_task\`, \`wg_task\`, \`netio_task\` — доли времени CPU, зарегистрированные FreeRTOS для задач \`wifi\`, \`tiT\` (tcpip_thread), \`ml_wg_mgr\`, \`ml_net_io\` соответственно. Если задача отсутствует/счётчик сброшен/данных недостаточно, возвращаем **-1**, а не выдуманный 0%.
- \`tasks\`, \`prof\` — число задач и валидность снимка. Первый после старта snapshot **только устанавливает базу** (CPU=-1), со второго появляются интервальные проценты.
- Используется \`CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS=y\`, уже включённый в проекте. Заранее ограниченный 64 задачами массив выделяется **один раз** в PSRAM. Не запускаются дополнительные периодические задачи. В каждой 10-сек итерации вызывается \`uxTaskGetSystemState\`; этот сборщик приостанавливает планировщик на короткое время, поэтому потенциально немного влияет на измерения.

### Что НЕ измеряется

**Официальный публичный API ESP-IDF на используемой версии не даёт надёжного счётчика MAC retries, реальной доставки Wi-Fi TX или точного PHY airtime для каждого WG пакета.** \`udp_sendto\` success означает принятие пакета сетевым стеком, НЕ успешную передачу в радиоэфир. Wi-Fi RSSI — показатель качества сигнала к AP, а не доказательство отсутствия помех или потерь. Считать \`cpu0_busy\` равным 100% узким местом можно только вместе с данными задач, очередей и производительности.

## Безопасность и контроль

\`wg5_diag.c\` подключается только в **generated build copy** компонента через \`REQUIRES esp_wifi\`, в основном приложении, интерфейсе и неизменяемом pinned submodule исходников правок нет. Старые wgopt1/wgopt2/wgopt4 path instrumentation и криптографические алгоритмы идентичны. Строка \`WG5_SYS\` собирается каждые 10с независимо от пользовательского API; не содержит токенов, секретов, адресов или содержимого пакетов.

CI тестирует C-реализацию через mocks (\`esp_wifi_sta_get_ap_info\`, \`esp_wifi_get_ps\`, \`uxTaskGetSystemState\`), корректный baseline, дельты обоих IDLE, задачи, ошибку переполнения 64, одно PSRAM выделение и отсутствие Wi-Fi изменений. Все старые regression, безопасность и OTA source/image/provenance проверки обязательны. Hardware acceptance *pending* до фактического теста.

## Порядок одного испытания

1. Сохранить работоспособный \`wgopt4\` BIN (в крайнем случае откатиться на \`wgopt2\`). Проверить SHA256 wgopt5 BIN по \`SHA256SUMS.txt\` из CI; не путать digest ZIP и digest самого BIN.
2. Установить **только OTA BIN** \`firmware-0.1.35-tuya-wgopt5-esp32-s3-ota.bin\` через WebUI, **без factory, NVS reset, re-partition**. Проверить, что STA, WebUI и Tailscale работают, \`192.168.0.146\` доступен.
3. В офисе \`iperf3 -s -B 192.168.0.146\`; локальный Tailscale Windows выключен. Дома \`iperf3 -c 192.168.0.146 -R -t 120 -i 10\`.
4. Сразу после завершения открыть Logs / Журнал ESP32. Экспортировать всю доступную историю, особенно строки \`WG4_TX\`, \`WG4_RX\`, \`WG5_SYS\` с \`t_ms\` и вывод \`iperf3\`. Веб-кольцо 16KiB ограничено: если записи уже перезаписаны, следует собирать их в процессе теста.
5. Сопоставить окна по времени. Снижение RSSI/смена канала/изменение PS подтверждают корреляцию радиопараметров. Высокая загрузка + рост очередей — возможный scheduler bottleneck. Если изменений нет, следующий этап — отдельное проверочное TCP/UDP измерение для локализации уровня потерь/ограничений.

Любая нестабильность — OTA откат на сохранённую **wgopt4** без сброса NVS. **Увеличения скорости пока не заявляем: wgopt5 только измеряет.**
