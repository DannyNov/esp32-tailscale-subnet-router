# wgopt8: точные коды direct TX errors

База: wgopt7, коммит 521b8a7bb395ba3bb22797f579d1c8ef1f57860c.
RX FIFO остаётся 128. Изменения касаются только пассивной диагностики.

`WG4_TXERR` на WARN показывает `t_ms`, фактическое `window_ms`, `bucket`,
`raw_err` и `delta` для каждого непустого bucket direct WG transport data.
Коды 0..-16 представлены отдельно; bucket=17/raw_err=127 означает other,
а не реальный код 127. Код 0 означает принятие нижним путём, не доставку.
Keepalive включены; handshake type 1..3 и DERP исключены.

Массив из 18 atomic uint32_t занимает 72 байта BSS; время предыдущего окна
добавляет 8 байт, всего 80 байт данных без возможного linker padding.
Снимок bucket занимает ещё 72 байта стека reporter. Reporter атомарно
обнуляет каждый bucket при чтении. Без динамической памяти и UART в hook.
При одновременном обновлении старого WG4_TX отдельные события на границе
могут попасть в соседние окна; отдельная строка не является общим снимком
всех счётчиков. Первое окно отсчитывается от старта esp_timer.
До 18 строк на существующий цикл reporter, обычно одна успешная и
несколько ошибок. Новых периодических задач нет.

Borrowed-pbuf callback теперь также вызывает `wg_diag_tx(3, err)` после
`udp_sendto`: это заполняет существующий INFO tx_stage=udp_sendto.
Ранние ERR_CONN/ERR_VAL до udp_sendto остаются видны в WARN-гистограмме.
При WARN runtime INFO-строки могут быть скрыты.

ERR_MEM сам по себе не доказывает нехватку Wi-Fi TX buffers: он может
возникнуть выше драйвера. Точное место отказа потребует следующего probe
только после получения кодов. Ошибка не приписывается конкретному peer
или TCP-потоку. Алгоритмы crypto, маршрутизация, RX drain и ownership
буферов не изменены.

Сборка OTA-кандидата без автоматической прошивки устройства.
