# Аудит WG RX и диагностический кандидат snapoff1

14 октября 2026, МСК. Устройство не прошивалось, настройки не менялись, перезапуск не выполнялся. Main и upstream microlink не изменены.

## Основание и предел подтверждения

По данным пользователя после восстановления прямого Windows UDP: direct RX drop +39/2247 (1,74%), затем +96/3472 (2,76%); за примерно 50 с +138. DERP RX +0, direct TX тысячами пакетов, tx_err +0. Полный новый лог в текущем запросе отсутствует; эти числа — предоставленные наблюдения, не результат нашего измерения. Старые доступные вложения и краткий контекст беседы не подтверждают новый аппаратный результат.

Исходник pinned microlink `2c796e3b14872b94fb2c54102affaacb1cc4a77b`, `components/microlink/src/ml_wg_mgr.c`: функция `dump_wg_state_snapshot()` печатает несколько ESP_LOGI строк, а `ml_wg_mgr_task()` вызывает ее раз в 10 с после второго RX drain. Комментарий upstream прямо описывает блокировку consumer на UART 115200 примерно на 300 мс и переполнение очереди 32. Перенос уровня WARN -> INFO не решает проблему при включенном INFO. Механизм синхронного вызова подтвержден кодом; причинность конкретных потерь и улучшение SMB требуют аппаратного A/B теста.

При 225–347 пакетах/с очередь 32 покрывает только около 92–142 мс, если consumer не работает. За 300 мс приходят примерно 67–104 пакета. Это оценка по среднему входному потоку, а не точное моделирование burst, Wi-Fi или TCP.

## Минимальная стратегия

В существующем build overlay заменен только вызов `dump_wg_state_snapshot(ml)` на комментарий; `wg_diag_stack_sample()` сохранен. Сам upstream snapshot остается в скопированном исходнике как невызванная static функция. Обход peer/netif, форматирование строк и UART вывод snapshot больше не выполняются в consumer. Никакие указатели не передаются фоновой задаче; не добавлены задачи, очереди, heap allocations или копии mutable peer state. Поэтому новый snapshot не создает гонок, use-after-free, переполнения буфера или увеличения стека: он отключен. Это проверка отсутствия snapshot под нагрузкой, а не доказательство безопасности альтернативной фоновой реализации.

WG_DIAG сохраняет RX/enqueue/drop/dequeue, TX/error, decrypt/forward/replay/policy, queue HWM/depth, таймеры, источники, allocation failures и stack sample. Его существующий reporter работает отдельно с числовыми счетчиками и краткими critical sections; вывод происходит вне source lock. Он не обращается к peer/netif pointer. Значения счетчиков читаются по отдельности, поэтому окно не является атомарным снимком всей системы; sampled HWM может пропускать краткие пики, uint32 дельты предполагают менее одного полного оборота за окно. Эти ограничения существующей диагностики не менялись.

`vTaskDelay(pdMS_TO_TICKS(10))` сохранен. Он гарантирует CPU для задач меньшего приоритета и предотвращает описанную upstream watchdog starvation. Оба WG drains, их burst=64 и budget=30 мс, DISCO budget и periodic/probe обработка сохранены. При 225–347 пакетах/с за 10 мс в среднем прибывают 2–4 пакета; burst и задержки криптографии все равно могут заполнять очередь. Удаление yield, увеличение очереди или изменение budget смешало бы причины и добавило риск.

Синхронные DISCO summary, SLOW warnings и другие логи microlink остаются; общий UART/log lock может продолжать влиять на RX. Патч устраняет конкретный дорогой WG_SNAP, а не все возможные причины низкой скорости.

## База и сохранение derphdr1

Диагностическая база `5ad09418064050395c8c647de5f3c08ba590d24f`, наследующая integration/v0.1.33-tuya. В candidate включен прежний локально проверенный overlay derphdr1: частичный DERP header, BIO WANT/timeout, EOF, deadline, unsigned length. Он нужен для соответствия работающему firmware `0.1.33-tuya-wgdiag1-derphdr1`; это сохранение уже используемого поведения, не новое решение SMB. Перенесенный код проверяется теми же 37 C-регрессиями. Версия кандидата `0.1.33-tuya-wgdiag1-snapoff1` умещается в app description и включает derphdr1.

Скрипт overlay проверяет pin и чистоту upstream, точное число якорей и воспроизводимость. Исходные sdkconfig.defaults, partitions.csv, platformio.ini, main/, компоненты приложения, маршруты, ACL, peer auth, ключи, Omada и Tuya не редактировались. Изменения ограничены build scripts, host tests, версией и отчетом.

## Проверки и сборка

Результаты сборки и итоговые хэши приведены в `WG-SNAPSHOT-RESULT-RU.md`. Исполняемый host test извлекает точный periodic block из generated consumer, компилирует без snapshot/peer/netif declarations и выполняет 10000 окон. Это не симуляция реального FreeRTOS или измерение UART.

GitHub workflow `build-wg-diagnostics.yml` сохранен и расширен regression/image проверками; ветка изолирована, permissions contents:read, никакого deploy/release шага. CI включает прежний pthread telemetry test, который локальный runner Windows без cc пропускает. Отсутствие локального pthread теста нужно учитывать независимо от успешной ESP32 сборки.

## Риск и откат

Риск низкий: теряется подробный WG_SNAP peer/keypair state для этого диагностического кандидата, но не WG_DIAG. Изменение не обещает устранить все RX drops. Откат исходников — возврат к диагностической базе; возврат поведения текущего firmware должен также сохранить derphdr1 overlay. Уже работающая прошивка на устройстве не изменена, поэтому аппаратный откат сейчас не требуется.

## Следующий smoke test — только после отдельного согласования

Предложение: согласовать прошивку кандидата и повторить идентичное SMB скачивание 2–3 минуты при подтвержденном direct UDP, затем сравнить с текущим derphdr1. Сохранить 10-секундные WG_DIAG окна, скорость/время передачи, TCP retransmissions на Windows, direct/DERP byte counters, queue HWM, process/loop slow30, heap/stack и coredump. Убедиться, что WG_SNAP отсутствует, DERP остается исправным при отдельной проверке fallback, нет reboot/crash и деградации Tuya. Критерий успеха — воспроизводимое уменьшение drop/rx и улучшение устойчивой скорости, а не один пик. Прошивка, переключение пути и перезапуск в этом аудите не выполняются.
