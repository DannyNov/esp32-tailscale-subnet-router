# wgopt3 — отдельный эксперимент с mbedTLS ChaCha20-Poly1305 для WireGuard data

**Версия:** `0.1.35-tuya-wgopt3`. Основание: `wgopt2` commit `0769828dc36266ceae92e4774b6d512336e1d658`, pinned microlink `eb63b97073e529d57bc9c1deaeea25ac304034e5`. Изменения только в generated build-copy; исходный submodule, `main` и production releases не меняются.

## Почему выбран именно такой этап
По аппаратным данным `wgopt2` офис → дом 7.20 Мбит/с (30 с), дом → офис 5.88 Мбит/с (120 с); устранение лишней RX-копии не привело к заметному росту. В предыдущей диагностике TX Crypto занимал ~445 мкс/пакет и RX Decrypt ~199 мкс/пакет. Используется `crypto/refc/chacha20poly1305.c`, программная реализация без аппаратного ускорения. В ESP-IDF уже включён `CONFIG_MBEDTLS_CHACHAPOLY_C=y`, а `CONFIG_COMPILER_OPTIMIZATION_PERF=y`, поэтому можно испытать штатный mbedTLS backend без дополнительной криптографической библиотеки.

## Реализация
Вне оригинального microlink создан build-only `src/wgopt3_crypto.c`, подключён через CMake с `REQUIRES mbedtls`. Только **data frames (type=4)**:
- TX: `wireguardif_output_to_peer` шифрует `wgopt3_encrypt_data` (mbedTLS ChaChaPoly), потом увеличивает `sending_counter` ровно на 1 **только при успешной аутентифицированной шифрации**. Если API вернул ошибку, пбуфер освобождается и пакет НЕ отправляется.
- RX: `wireguard_decrypt_packet_diag` проверяет тег `mbedtls_chachapoly_auth_decrypt`, и **только после его успеха** исполняет тот же `wireguard_check_replay`. При неуспешной проверке пакет отвергается без обновления WG replay state.
- IV полностью совместим с WG: 12 bytes `00000000 || LE64(counter)`. Выход in-place допустим; тег 16 B после ciphertext. Handshake, MAC, X25519, cookies, XChaCha, peer lookup, DERP, subnet routing, счетчики диагностики и UI не изменены. Историческая refc реализация сохранена для control path и для сравнения в host test.
- Тесты используют фактический compiled `wgopt3_crypto.c` через system libmbedcrypto, сверяют последовательности с исходным refc, независимо рассчитанный `ChaCha20Poly1305` KAT (Python cryptography), нулевые данные, разные длины, in-place, битые MAC и большие nonce.

## Ожидания и ограничения
mbedTLS тоже программный на ESP32-S3, поэтому не гарантируется, что он быстрее refc. Шифрование data и проверка тега защищены тестами, но аппаратная производительность и устойчивость под длительной нагрузкой должны быть проверены. Не интерпретировать отсутствие ошибок CI как подтверждение прироста скорости.

## OTA и откат
Сохранить проверенный `wgopt2` BIN. Сверить `SHA256SUMS.txt` из архива CI с текущим `firmware-0.1.35-tuya-wgopt3-esp32-s3-ota.bin`. Загрузить **только OTA BIN**, не factory; не сбрасывать NVS, не трогать ключи и tailnet. После перезагрузки проверить Tailscale, Wi-Fi, домашний доступ к офисному `192.168.0.146`, WebUI и Tuya. При сбоях вернуться через WebUI на `wgopt2`.

Для одного сравнения скорости: на офисном Windows Tailscale OFF, iperf3 server `iperf3 -s -B 192.168.0.146`, на домашнем `iperf3 -c 192.168.0.146 -R -t 120 -i 10`. Ранее в направлении офис → дом `wgopt2` дал 7.20 Мбит/с (30 с); длительности отличаются — сравнение предварительное. При необходимости провести аналогичный 30-с тест, но не требовать дополнительных провайдерских проверок. Если медленнее, развернуть `wgopt2` и использовать результаты для следующего этапа.

**Не менять рабочую прошивку автоматически.**
