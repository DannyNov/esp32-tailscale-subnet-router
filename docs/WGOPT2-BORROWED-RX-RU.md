# wgopt2 — приём зашифрованных WG-пакетов без повторного копирования

**Кандидат:** `0.1.35-tuya-wgopt2` — продолжение работающей `wgopt1`. Платформа: ESP32-S3 N16R8, Tailscale subnet router, прямое магическое UDP и DERP.

## Вывод по исходникам
В проекте уже включена `CONFIG_COMPILER_OPTIMIZATION_PERF=y`. В библиотеке применяется корректный программный ChaCha20/Poly1305; замена криптографии без независимых векторов проверки и инструментальных замеров внесла бы дополнительный риск. Поэтому следующий безопасный hot-path — **входящий encrypted WG packet**. До патча при каждом приёме `wg_mgr` создавал PBUF_RAM, копировал туда уже принятый `pkt->data`, и немедленно вызывал синхронный `wireguardif_network_rx`. Сам WireGuard отдельно создаёт **новый PBUF_RAM для расшифрованного IP-пакета**, который уходит в асинхронный `tcpip_input`.

## Что меняем
Для полного пакета WireGuard type=4, reserved bytes=0, длины от 32 до 65535 включительно `wg_mgr` передаёт уже живой буфер `pkt->data` в новый синхронный `wireguardif_network_rx_borrowed`. **Не создаёт промежуточный PBUF_RAM**, а после возвращения обработчика ровно один раз освобождает внешний encrypted buffer. Базовая функция `wireguardif_network_rx` продолжает принимать owned-pbuf и освобождать его сама, вызывая тот же обработчик. Вызовы handshake/cookie/неполных данных идут прежним PBUF_RAM путём. Для DERP `addr` остаётся 0.0.0.0; для direct src IPv4/port исходные. Нет изменения replay, MAC, AEAD, rate-limit и state WG.

**Граница безопасности:** входящий зашифрованный пакет используется только в момент синхронного парсинга. `wireguardif_process_data_message` продолжает расшифровывать в отдельно выделенный PBUF_RAM, который в случае успешной аутентификации/проверки cryptokey routing передаётся `tcpip_input`. Никакого указателя на освобождённый encrypted buffer в lwIP не остаётся. Старая система аллокаций/телеметрия `rx_pbuf` и `rx_copy` теперь относятся только к старому резервному/control пути, не к обычному WG data. Учитывать при сравнении wgdiag метрик.

## Проверки и ограничения
Host regression проверяет фактический сгенерированный код, точную ветку обработки, сохранённые wrapper/pbuf_free и независимую память для decrypted pbuf. Host-C harness запускает извлечённый в точности fast-path с mock data/DERP адресами и проверяет передачу входящего указателя/его освобождение ровно один раз, обход handshake/cookie/невалидных пакетов. IDF CI компилирует итоговую ESP32-S3 OTA app, проверяет ESP image SHA256, app descriptor version, partitions, pinned external microlink and unchanged production config.

**Ожидаемый эффект ограничен:** по прежнему wgdiag4 `rx_pbuf+rx_copy` всего несколько десятков мкс на пакет, так что обещать скачок скорости в разы нельзя. Основной `tx_crypto` и `rx_lwip` остаются. Нет доказательств прироста скорости, пока не будет одного аппаратного iperf3 после OTA.

## Аппаратный smoke-test
Сохранить работающий `wgopt1` BIN для отката. В WebUI установить только `firmware-0.1.35-tuya-wgopt2-esp32-s3-ota.bin` из CI ZIP (не factory), после сверки SHA256 с `SHA256SUMS.txt`; не сбрасывать NVS. Проверить Status/Tailscale/Wi-Fi/Tuya/доступ к `192.168.0.146`. Отключить Tailscale на офисном Windows, запустить там `iperf3 -s -B 192.168.0.146`; на домашнем Windows `iperf3 -c 192.168.0.146 -R -t 30 -i 5`. Сравнение: wgopt1 **6.78 Мбит/с** по одному измерению (ранее wgdiag4 5.87). Без новых проверок операторов/провайдеров.

Если прогресс отрицательный, сеть/handshake нестабильны или есть падения, вернуться WebUI OTA к сохранённому `wgopt1` без очистки NVS. Не выполнять factory/reset/repartition.

**Политика:** main, releases, отдельный microlink submodule, NVS, keys, DHCP, Tuya, настройки subnet routing, выход в Интернет и выполняющаяся прошивка не меняются.
